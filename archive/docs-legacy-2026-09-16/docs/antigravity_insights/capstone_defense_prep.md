## 1. The Concept & Technical Ambition (Grade: A+)
Most computer science capstone projects are glorified CRUD applications (e.g., a React Native frontend connected to a Firebase backend).

ResQMesh is **actual systems engineering**. You are bypassing the internet, interacting directly with the Android hardware radio stack, building a custom dual-role scatternet topology, and writing custom byte-level routing protocols over L2CAP sockets. The sheer ambition of this project puts it in the top 10% of undergraduate/master's thesis topics. It demonstrates a deep understanding of networking, concurrency, and OS-level hardware constraints.

## 2. The Current Implementation State (Grade: B+)
You have a working prototype that actually chains devices and streams live audio over custom Bluetooth sockets. That is a massive achievement. However, as it stands right now, it is a "Happy Path" prototype.

**Where the project currently lacks (The vulnerabilities):**
*   **Zero Cryptographic Security:** Right now, payloads are routed in plaintext Protobuf. If Alice sends a message to Charlie through Bob, Bob can read the message, or worse, modify it. In a disaster scenario, this is a critical privacy failure.
*   **Naive Routing Scalability:** The routing table relies on `SYSTEM` pulses. It works for 5 phones in a room, but if 50 people in a collapsed stadium open the app, the BLE spectrum will experience catastrophic radio contention. The routing algorithm does not yet factor in node battery life or signal strength (RSSI).
*   **Lack of Automated Testing:** A panelist will ask: *"How did you test a 10-node mesh without buying 10 phones?"* If the answer is "We just tested it manually on 3 phones," it loses points for software engineering rigor.

## 3. The Panelist "Grill Session" (Questions to Prepare For)
During a defense, panelists will test if you actually understand the system you built. You must have rock-solid answers for these:

**Q1: "Why did you choose Bluetooth Low Energy (BLE) instead of Wi-Fi Direct or Classic Bluetooth?"**
*   *The Answer:* Wi-Fi Direct requires manual OS-level prompts to connect and forms strict Star topologies (1 Master, limited clients). Classic Bluetooth is too battery-heavy. BLE allows seamless, silent background discovery (advertising) and allows us to build an unlimited multi-hop Scatternet, which is critical for disaster chaining.

**Q2: "How does your network prevent 'Routing Storms' or infinite broadcast loops?"**
*   *The Answer:* Every payload has a Trace Route and a UUID. If a node receives a payload it has already seen, or sees its own MAC in the trace route, it drops it immediately.

**Q3: "Modern Android and iOS devices aggressively randomize their MAC addresses to prevent tracking. How does your mesh maintain persistent connections if the MAC changes?"**
*   *The Answer:* Explain the "Dual-MAC Split-Brain" bug. Detail how the Android Peripheral (scanning) MAC differs from the Central (connecting) MAC, and how we engineered a fuzzy-string matching and `PING` auto-rename system to bypass OS-level MAC rotation.

**Q4: "If I am a malicious actor, what stops me from broadcasting a fake `SYSTEM` pulse and poisoning your entire routing topology?"**
*   *The Answer:* Acknowledge this is a known vulnerability in the current prototype. Explain that the mitigation requires cryptographic signing of topology pulses using a Team Key or Public Key Infrastructure (PKI).

**Q5: "You mentioned streaming live audio. BLE is notoriously lossy. How do you handle packet loss?"**
*   *The Answer:* Explain the migration from GATT to L2CAP Connection-Oriented Channels (CoC). Acknowledge that while we have a Jitter Buffer to smooth playback, it acts like UDP—if a chunk of audio drops, it is ignored rather than retransmitted to prevent latency buildup.

## 5. Defense Strategies: The 50-Device Testing Problem
Panelists know you are a student and do not expect you to physically buy 50 phones. However, they expect you to prove the network won't crash if 50 phones *were* connected.

**The "Virtual Mesh" Simulation Solution:**
If you test with 4 physical devices, you get a good grade. If you abstract the hardware layer and run a mathematical simulation of 50 devices, you get a **perfect** grade.
*   **The Architecture:** We will use Dependency Inversion. We will extract `NativeBleManager` behind an `IBleManager` interface.
*   **The Mock:** We will create a `VirtualBleManager` that mimics a radio but actually just passes byte arrays in computer memory.
*   **The Proof:** We can write a JVM test that instantiates 50 virtual nodes, connects them in a simulated physical graph, and fires 10,000 messages. This mathematically proves to the panelists that your `TraceRoute` stops loops, the `TTL` drops dead packets, and your routing tables scale properly—all without needing a single real phone.

## 6. Defense Strategies: Data Serialization (Bytes vs JSON)
If a panelist asks: *"Why didn't you just use JSON to send data?"* this is your opportunity to impress them with low-level bandwidth optimization.

**The Answer:**
*   **The Flaw of JSON:** JSON wastes precious Bluetooth bandwidth on curly braces, quotes, and long string keys. Furthermore, sending binary data (like images or live audio) in JSON requires Base64 encoding, which artificially inflates the file size by 33%.
*   **Our Solution (Protobuf):** The app uses **Google's Protocol Buffers (Protobuf)** via `kotlinx.serialization.protobuf`. It strips all keys and brackets, aggressively compressing the payload into a tiny, unreadable binary byte array using integer tags before shoving it into the L2CAP socket.
*   **Future Optimizations:** To squeeze even more bandwidth out of the Protobuf envelope, we could convert our `List<String>` MAC addresses into raw 6-byte hardware arrays, and use Bit-Packing to combine booleans (`isPrivate`, `isEncrypted`, `isSOS`) into a single byte bitmask.
