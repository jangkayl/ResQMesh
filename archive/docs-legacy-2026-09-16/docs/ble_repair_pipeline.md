## Phase 1: Define connection ownership and lifecycle

Problem: state for one physical link is scattered across MAC-keyed maps (`activeConnections`, `activeServerConnections`, `pendingQueues`, `isWriting`, buffers, MTU, timestamps, names, and counters). A disconnect can clear one map while leaving another map stale.

- [x] Define a per-link record with stable peer ID, endpoint, role, GATT/server-device reference, generation, lifecycle state, outbound queue, current operation, MTU, timestamps, and retry count. See Phase 1 evidence above; legacy endpoint maps remain until later phases.
- [x] Define allowed transitions: `DISCONNECTED -> CONNECTING -> DISCOVERING -> CONFIGURING -> READY -> DISCONNECTING -> DISCONNECTED`; add explicit failure paths. Server setup uses `CONNECTING -> CONFIGURING`; timeout and failure use `DISCONNECTING`.
- [ ] Assign a new generation for every physical attempt. Client callback/timer capture is implemented and tested; the shared server callback still has an ambiguous same-address late-event case.
- [ ] Decide one owner for state transitions and cleanup. Avoid independent callbacks and timers mutating shared maps without checking ownership.
- [x] Keep stable node identity distinct from a BLE MAC; `BleLink.peerNodeId` is separate from `BleLink.endpoint`.

Exit: every callback can identify the link it owns, and the app never treats a merely connected but unconfigured GATT link as ready.

## Phase 2: Protect new links from old callbacks

Problem: a late callback from an old `BluetoothGatt` can remove a replacement link's state because cleanup is keyed only by MAC.

- [ ] Before any callback changes state, compare its actual GATT reference and generation with the current link.
- [ ] Ignore and log stale callbacks; close the old GATT reference when safe.
- [ ] Keep the `BluetoothGatt` returned by `connectGatt()` in a pending-attempt record.
- [ ] On connect timeout, disconnect/close that attempt and invalidate its generation before releasing the outbound connect lock.
- [ ] Cancel generation-bound timers when the attempt ends. A timer for an old attempt must never release a new attempt's lock.
- [ ] Give simultaneous client/server links a deterministic winner; finish cleanup of the losing link without touching the winner.

Exit: delayed timeout and disconnect callbacks from attempt N cannot change attempt N+1.

## Phase 3: Make disconnect cleanup complete

Problem: the server disconnect currently removes the active socket and identity fields but can leave `pendingQueues` and `isWriting`. On reconnect, `putIfAbsent` may preserve `isWriting = true`, so `processNextPayload()` never advances.

- [ ] Create one idempotent cleanup path for client, server, forced disconnect, timeout, and stop-node events.
- [ ] Clear or replace the queue, in-flight flag, chunk buffer, MTU, write-failure count, interaction time, establishment time, identity mapping, socket, and connection-owned timers.
- [ ] Check ownership/generation before deleting a MAC-keyed entry. Cleanup of a losing connection must not delete a newer one.
- [ ] Start every reconnect with a fresh queue and `writeInFlight = false`; avoid `putIfAbsent` for state that belongs to a new physical connection.
- [ ] Make UI disconnect and route updates follow the verified connection transition once, not multiple callback paths.

Exit: disconnect is safe to invoke twice, and reconnect can send a payload immediately after reaching `READY`.

## Phase 4: Serialize outgoing payloads

Problem: server notifications advance after 20 ms without `onNotificationSent()`. Client no-response writes use a 30 ms fallback. Fixed delays do not prove that Android finished an operation.

- [ ] Server: send one notification, hold one in-flight item, and advance only when `onNotificationSent(device, status)` reports completion.
- [ ] If the notification API rejects a send or completion reports failure, retry with bounded backoff for that same item; classify an exhausted retry as a transport failure.
- [ ] Client: select a write mode and completion rule supported by the target devices. Advance from its callback when available; use a generation-bound timeout to fail/recover an operation rather than declaring it complete.
- [ ] Give every queued item an operation ID so duplicate callbacks and timeouts cannot advance twice.
- [ ] Apply queue bounds and traffic priority so `SYSTEM`, `PING`, SOS, text, image, and live audio cannot indefinitely starve one another.
- [ ] Preserve payload order during retry; do not replace a live queue while another thread can enqueue into it.

Exit: one GATT send per link is in flight, callbacks advance the queue exactly once, and retries cannot silently drop or reorder items.

- [ ] Start optional L2CAP PSM discovery only when it cannot overlap a required GATT operation.
- [ ] Distinguish failed API initiation from callback failure and callback timeout in logs and retry handling.
- [ ] Gate `sendSystemPulse()` and `processNextPayload()` on `READY` for that link.
- [ ] Bound inbound GATT frame lengths and accumulated chunk buffers on both client and server; reject malformed or oversized frames before allocation or Protobuf decode.
